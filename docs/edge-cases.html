3. The fix

  1. Measure how much data backs each situation

    Function
    support_grid, support_of

  2. Add a model that does not need to have seen the situation

    Instead of learning the chance of winning from a state, the simulation learns the chance of each outcome of a single delivery, then works out the chase exactly.

      Functions
      delivery_table, fit_outcomes, solve, fit_calibration

    • Blend the two according to the data

      Function
      calculator_table, blend_weight

    • Make the answers obey cricket logic

      One more run needed, one ball fewer or one wicket fewer should never raise the chance. Gluing two models together can break this, so the final table is replaced by the average of its tightest monotone upper and lower bounds. This moves values only where they disagree with a neighbour.

      Function
      monotone_envelope

    • Never print a certainty for an open chase

    Accuracy after the fix (post-test check)

    Browser matches Python

    The calculator is computed in your browser. A test (parity.test.mjs) rebuilds the whole table in JavaScript and compares it with Python on 250 random situations; they agree to within a billionth.

    6. What this does not fix

    • The simulation treats deliveries as independent given the score, phase, wickets and required rate. It ignores who is batting, free hits and pressure, so it is a reasoned guess where data is missing, not a measurement.
    • Situations no chase reached cannot be checked against real results. The numbers there are plausible, not proven.
    • The replay and the main results use the models as chosen before the test run; only the calculator uses this fix.
